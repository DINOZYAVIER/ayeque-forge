# AGL-202: Dynamic Conversation goal during compaction

## Status

Draft. The desired LLM-owned goal refresh is a human decision. The fallback
and public-observability choices at the end remain open and block
implementation where noted.

## Problem

`SemanticSummary.objective` is the only durable semantic field that represents
what a Conversation is currently trying to achieve. It is generated by the
compaction request in
`products/services/agl-daemon/src/agent/compaction.rs` and stored inside the
internal compaction message in SQLite.

The current summary instruction says to preserve "the human objective". When a
Conversation changes direction, that wording encourages the model to repeat an
early objective from an older summary instead of describing the work that the
Conversation is now pursuing. A later compaction then receives that stale
objective as historical input and can preserve it again.

The result is a valid but semantically stale compacted context: the exact Store
history remains intact, while the context restored for the next model call can
say that the Conversation is still pursuing its first goal.

## Desired outcome

At every successful LLM-generated compaction,
`SemanticSummary.objective` states the current goal of the Conversation at the
compaction boundary.

The summarizer determines that goal from the whole summarized semantic
narrative, including any previous summary and the newer human/assistant turns.
It may retain the previous objective when the later conversation continues the
same work, refine it when scope changes, or replace it when the human redirects
the conversation.

This happens in the existing compaction inference call. There is no second
goal-classification call and no separate mutable Conversation-goal record.

## Existing contracts retained

- Full messages, tool results, operations, and compaction records remain
  durable in SQLite.
- `CompactionExactState` remains daemon-authored and is not inferred by the
  model.
- The semantic output remains one `SemanticSummary` JSON object with
  `objective`, `rationale`, `decisions`, `discoveries`, `unresolved`, and
  `next_position`.
- Every semantic claim remains nonempty and source-bound through
  `SemanticSummary::validate`.
- Summary generation uses the selected Function model and the existing
  compaction budgets, correction attempt, reasoning policy, and tool-free
  request.
- A goal update does not rewrite previous messages or previous compaction
  records. The latest successful compaction is the current compacted view.

## Terms

`objective` is the current outcome the Conversation is trying to reach.

`next_position` is the immediate continuation point: what has just been done
and what action or answer should happen next. It can be narrower than the
objective but must not contradict it.

Completed earlier goals belong in `decisions` or `discoveries` when they remain
relevant. They are not retained as the current objective merely because they
were the original request.

## Summary instruction changes

Replace the ambiguous requirement to preserve "the human objective" with an
explicit current-goal rule:

1. Infer the current Conversation objective at the end of the supplied
   history, not merely the first stated objective.
2. Treat a previous `SemanticSummary.objective` as historical evidence, not as
   immutable authority.
3. Give later explicit human redirections precedence over earlier goals.
4. Use assistant actions, tool results, and unresolved work to determine the
   present state, but do not let an assistant silently invent a new goal that
   the human did not request or accept.
5. If later turns complete one goal and begin another, put the new active goal
   in `objective` and preserve only still-relevant consequences of the old goal
   in the other fields.
6. If no later turn changes the goal, retain it concisely rather than
   paraphrasing it into a different requirement.
7. Make `next_position` describe the next work under the inferred current
   objective.

The response remains the existing single JSON object. No additional model
output field is introduced.

## Source attribution

The inferred objective must cite messages that justify the current goal.

- When a newer user message redirects the Conversation, its original message
  ID must be among `objective.sources` if that message is in the summarized
  prefix.
- When the current goal is carried from an earlier compaction, the previous
  internal compaction message may be a source because it is part of the current
  compaction source set.
- Sources do not make the text authoritative by themselves; they provide an
  auditable link to the narrative used by the LLM.
- Existing validation continues to reject unknown or empty source lists.

No deterministic keyword classifier is added. Semantic goal changes such as
"forget that", "instead", a correction, or an implicit transition after
completion are interpreted by the summary LLM under the instruction above.

## Compaction chain behavior

For a first compaction, the model infers the objective from original
Conversation messages.

For every later compaction, the model receives the previous semantic summary
as historical content plus the newer prefix messages selected by the current
compaction algorithm. The new summary replaces the previous compacted view in
the context reconstructed by
`products/services/agl-daemon/src/store/agent/compaction.rs`; the previous
record remains durable in SQLite.

Therefore the current objective evolves as:

```text
previous semantic summary + newer summarized messages
                         |
                         v
              one compaction LLM call
                         |
                         v
       new SemanticSummary.objective + next_position
```

## Validation and failure behavior

Structural validation remains deterministic. The daemon can validate JSON
shape and source IDs, but it cannot deterministically prove that an inferred
goal is semantically correct.

An invalid model result follows the current behavior: one correction attempt,
then the deterministic compaction fallback where currently permitted. The
fallback must not fabricate a newly inferred goal.

The implementation must not reject an otherwise valid summary merely because
the objective text differs from the previous objective; such a difference is
the intended behavior when the Conversation changes direction.

## Implementation scope

Expected changes are localized to:

- `products/services/agl-daemon/src/agent/compaction.rs`: revise the summary
  instruction and deterministic fallback after the fallback decision below;
- `products/services/agl-daemon/src/agent/compaction_tests.rs`: cover retained,
  refined, and replaced objectives across multiple compactions;
- optionally `crates/agl-core/src/agent/compaction.rs` only if a decided
  validation rule requires a type-level change.

No schema migration is expected for the selected design because
`SemanticSummary.objective` and the durable compaction JSON already exist.

## Acceptance tests

1. An unchanged task produces a later summary whose objective still expresses
   the same goal.
2. A later explicit user redirection produces a later summary whose objective
   expresses the new goal and cites the redirection message.
3. A completed first task followed by a new task does not keep the completed
   task as the current objective.
4. A refinement of scope updates the objective without discarding still-active
   constraints and accepted decisions.
5. A previous summary is treated as input evidence: a second compaction can
   replace its objective based on newer messages.
6. `next_position` remains consistent with the new objective.
7. Unknown source IDs, empty objective text, malformed JSON, and tool-call
   output retain their current rejection behavior.
8. Restarting the daemon reconstructs the same latest objective from SQLite;
   compaction does not depend on process memory.
9. Full original messages and earlier summary records remain queryable after
   the objective changes.
10. Summary generation still consumes one model call per attempt and invokes
    no tools.

Tests should use controlled inference fixtures that return explicit summary
objects. They verify daemon behavior and prompt contents; they must not depend
on a nondeterministic live model choosing particular prose.

## Non-goals

- A user-editable Conversation-goal API.
- A separate goal table or mutable goal column.
- RAG over historical messages.
- Rewriting old summaries when the goal changes.
- A second LLM call dedicated to goal classification.
- Deterministic phrase matching for goal changes.
- Exposing the objective in CLI or daemon public responses unless that is
  separately decided.

## Open human decisions

### D1. Goal when semantic generation falls back

The current deterministic fallback uses an excerpt of the first summarized
message as `objective`, which is the stale-goal behavior this task is intended
to avoid.

- **A — carry the latest valid objective (recommended):** if the source prefix
  contains a previous valid compaction summary, copy its objective; otherwise
  use the latest summarized user-message excerpt. This never claims that a
  failed LLM inferred a new goal, but a redirection in the failed compaction is
  only approximated when no previous objective exists.
- **B — latest user-message excerpt:** always use the latest summarized user
  message. This reacts to redirection but can mistake a narrow answer or
  clarification for the overall goal.
- **C — fail compaction:** do not commit a deterministic semantic fallback when
  the model cannot produce a valid summary. This preserves semantic purity but
  can leave the Conversation unable to continue under context pressure.

This decision changes observable failure/recovery behavior and must be chosen
before implementation.

### D2. Public goal visibility

- **A — internal summary only (recommended):** the current objective affects
  restored model context and remains inspectable through stored compaction
  data; no CLI/API surface is added.
- **B — expose latest objective:** add a typed daemon projection and CLI output
  for the latest compacted objective. This creates a new public API and requires
  separate naming and absence semantics before implementation.

This decision does not block the summary-instruction change when A is chosen;
B expands the task materially.

## Completion gate

The spec is ready for implementation only after the human selects D1 and D2
and explicitly confirms that this decision set is complete.
